Observations specific to this machine/run (small model, n=100, single
process -- not a claim about Windows/CUDA behavior):

- AOTInductor's model *load* is much slower here (~148ms vs ~10-17ms for
  TorchScript) -- consistent with it including package unpacking, but
  its steady-state *inference* is comparable to or slightly faster than
  TorchScript once past the first call.
- AOTInductor's *first inference* is notably faster than TorchScript's
  (no separate JIT warm-up cost baked into the first call the way
  TorchScript's interpreter has), the opposite of load time.
- AOTInductor artifacts (`.pt2`) are roughly 5-10x larger on disk than
  the equivalent TorchScript `.pt` for these tiny models.

## Known Limitations

- Only macOS (Apple Silicon, CPU) has been exercised end-to-end in this
  repo's history so far. Windows x64 Release (the primary target) and
  any Linux/CUDA path are implemented and documented but
  **NOT_YET_TESTED_ON_THIS_MACHINE**.
- TorchScript: only `torch.jit.trace` was validated, not `torch.jit.script`.
- AOTInductor: the compile/package/load API
  (`torch._inductor.aoti_compile_and_package` /
  `torch._inductor.aoti_load_package`) lives under the private
  `torch._inductor` module in PyTorch 2.13.0 -- no public alias exists.
  Treat it as subject to change across PyTorch versions.
- No intermediate-layer parity was implemented; only final-output parity
  (per spec, to keep scope bounded).
- CUDA memory-leak-trend analysis is unproven on any machine yet (no
  CUDA GPU was available in this session).

## Recommended Backend (based on this run only)

On this machine, **both backends passed everything that was actually
testable** (build, CPU inference, parity, 100x stability, clean rebuild).
Per the spec's decision rule, this macOS/CPU-only result is **not
sufficient by itself** to recommend a default backend for the primary
Windows/CUDA target -- it demonstrates AOTInductor is not universally
broken (it works end-to-end on at least one Apple-clang/arm64/CPU
configuration with PyTorch 2.13.0), which is a meaningfully more
positive starting point than "assume it's broken on Windows," but the
actual Windows MSVC/CUDA probe (`cpp/aoti_probe` run on Windows x64
Release with a CUDA-enabled LibTorch) is the result that should decide
the primary-backend recommendation, and that probe has not been run yet.

**Until the Windows probe runs:** treat TorchScript as the safe default
(deprecated but proven compatible across more LibTorch distributions
historically) and AOTInductor as a promising but not-yet-Windows-verified
candidate, and re-run `scripts/build_aoti.py --probe-only` +
`probe_aoti` on the actual Windows 11 / VS2022 / CUDA machine before
finalizing the recommendation.
